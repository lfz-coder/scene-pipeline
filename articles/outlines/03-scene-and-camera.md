# 文章 03 提纲：场景类只写业务

状态：详细提纲。依赖 M3，正文中的完整场景源码和交互记录需在实现完成后固定版本。

## 读者任务与判断

读者用已经封装的模块搭建多个物体组成的场景，独立改变物体的位置和材质，切换 Orbit / Fly 相机，并新增第二个场景。

核心判断是：网格、材质和实例的共享关系应该分别表达；Camera 保持纯数据和矩阵职责，控制器处理输入。这能让模型导入、更多相机控制和风格管线接入同一份场景数据。

适用范围为简单 Scene 容器和单视口。父子层级、复杂 ECS、完整动画系统随真实需求加入。

## 正文推进

### 一个物体需要什么

用两个立方体举例：同一个 MeshId、不同 Transform；使用同一个 MaterialId 会共同变化，cloneMaterial 后独立编辑。通过界面实际操作证明共享语义。

对象图展示 `Entity → Transform / MeshId / MaterialId`，再连到 AssetStore。说明实体 ID 适合长期保存，容器中的引用不适合跨结构修改保存；工程存档也不能直接依赖运行时 ID。

### 从 Transform 到最终顶点

追踪 `SceneLayer::onUpdate → Transform::matrix → Renderer → uniform → vertex shader`。实际展示 T/R/S 顺序不同的结果，再给出统一约定的 `projection * view * model * position`。

链接已有矩阵课程，把篇幅留给“封装后矩阵在哪里产生、在哪里上传”。给定一个点做可核对的变换测试，避免仅检查函数返回了 16 个数。

### 相机能看，控制器决定怎么动

Camera 提供 lookAt 与 perspective，CameraControls 接收路由后的输入。分别展示鼠标旋转、滚轮、WASD 和 Orbit / Fly 切换；说明键盘位移为什么用 delta、鼠标位移为什么不重复乘 delta。

加入面板后验证：拖滑杆不旋转相机，输入名称不触发 WASD，切出窗口再回来不继续移动。用真实输入路径测试，不能只直接给 Camera 填参数。

### Renderer 读取场景，场景保持稳定

同一份 Scene 通过 Basic 和 Wireframe 管线绘制。展示绘制队列如何选择资源与矩阵，后续 Phong / Toon 只接入对应管线。UI 修改 CPU 参数，统一在帧内渲染，不在属性回调里拼 draw call。

### 添加第二个场景

完整展示第二个 SceneLayer：复用 primitive 和资源缓存，只改变实体组合、相机和运动规则。通过切换 / 清空验证旧 EntityId 失效而资源仍可复用。

## 必须收集的三组证据

1. 多实例共享网格、独立 Transform、共享 / 克隆材质的对比。
2. 矩阵行为测试，以及旋转 / 缩放 / 非法参数的实际检查。
3. UI 捕获输入、失焦清理、窗口缩放和两个相机模式的交互记录。

## 需要拆解的误解

- 一个 Mesh 就是一个物体；实际上几何资源与场景实例承担不同职责。
- Camera 越方便越应该直接读取 GLFW；这样会把相机绑到宿主与窗口输入，降低测试和复用能力。

## 读者带走的产物
