# 第五篇文章判断框架

- 核心立场：第二阶段应该扩展可复制的 CPU 状态和独立渲染 pass，让 Qt 只负责操作呈现；这样灯光、FBO 和未来执行者都能复用同一条链路。
- 误区一：把每种效果写进窗口回调就是封装。反例：GPU 生命周期随 UI 分散，替换宿主困难。当前由 Renderer 持有资源、Controller 校验数据。
- 误区二：FBO 纹理已经是屏幕颜色。两遍模糊重复 sRGB 编码会变亮；真实像素测试先失败再通过。
- 真实证据：Qt 新灯光增删改测试从缺控件失败变为通过；FBO 方向与双遍颜色测试暴露并修正问题；删除方向光的测试暴露旧 uniform 残留。截图与完整日志由最终验收保存。
- 适用边界：适合第一、二阶段的本地学习软件；不以 RGBA8 后处理冒充 HDR/PBR，不预先开发 AI 调度器。
- 读者产物：可运行无窗口配方、Qt 启动命令、CPU→GPU 调用链、文件行数检查和模块依赖表。
- 叙事：先让人玩到多灯光场景，再解释 CPU/GPU 边界、光照数学、FBO 输出，最后用失败测试与持久化约束说明设计为何必要。
- 价值自检：看完可在现有工程新增场景或滤镜，不需要复制窗口初始化和 GPU 上传代码。只产出中文；使用真实运行截图和可编辑 SVG，保留当前离线文章构建格式。
